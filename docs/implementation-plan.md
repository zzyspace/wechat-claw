# 开发实施计划

## 1. 目标

将项目按“可运行、可验证、可扩展”的节奏分阶段推进，优先做出一个稳定的报损日报 MVP，同时确保后续新增报账群等场景时不需要推倒重来。

## 2. 第一阶段交付物

第一阶段完成后，应具备以下能力：

- 机器人微信号成功登录
- 能监听指定报损群
- 能采集文本和图片消息
- 能将原始消息与图片落库/落盘
- 能调用模型提取报损结构化结果
- 能每天固定时间生成日报
- 能将日报发给你的主微信号

## 3. 任务拆解

### Milestone 1: 工程初始化

任务：

- 初始化 `Node.js + TypeScript` 工程
- 配置 `eslint`、`prettier`、`tsconfig`
- 建立目录结构
- 加入 `.env` 配置体系
- 抽象基础日志模块

产出：

- 可启动的空项目
- 基础配置和模块边界就绪

### Milestone 2: 微信接入验证

任务：

- 接入 `Wechaty`
- 完成扫码登录或会话恢复
- 监听消息事件
- 区分私聊、群聊、文本、图片
- 实现向指定联系人发送测试消息

验收：

- 能收到目标群测试文本
- 能收到目标群测试图片
- 能发一条“系统在线”消息给你的主微信

### Milestone 3: 原始消息存储

任务：

- 设计 SQLite 表结构
- 实现 `channels/raw_messages/message_attachments`
- 图片下载到本地
- 计算图片哈希
- 生成消息去重键

验收：

- 每条测试消息都能入库
- 图片可回溯到本地文件
- 重复消息不会重复入库

### Milestone 4: 场景路由与报损插件

任务：

- 实现 `Channel Router`
- 定义 `ScenarioDefinition` 接口
- 实现 `loss-report` 场景插件
- 建立报损场景 JSON Schema

验收：

- 目标群消息会路由到报损插件
- 非目标群消息可忽略或记录但不处理

### Milestone 5: 模型接入

任务：

- 封装模型 Provider 接口
- 接入 `Qwen3-VL-Flash`
- 接入 `DeepSeek-V4-Flash`
- 实现结构化提取任务
- 保存模型输出、置信度、错误信息

验收：

- 一条“图片+文字”消息能生成结构化报损记录
- 模型失败时任务可记录错误

### Milestone 6: 日报汇总与发送

任务：

- 实现按日聚合
- 统计高频物品、原因、待复核数量
- 实现固定模板渲染
- 可选接入总结模型润色文本
- 将日报发送到你的主微信号

验收：

- 每天定时发送一条日报
- 模型总结失败时仍能发送模板版日报

### Milestone 7: 稳定性增强

任务：

- 增加任务重试
- 增加登录状态监测
- 增加补跑日报命令
- 增加发送去重
- 增加结构化日志

验收：

- 模型接口短暂失败后可重试成功
- 某天日报可以手动补跑

## 4. 建议优先级

必须先做：

- 微信接入
- 原始消息存储
- 报损场景插件
- 日报汇总

可以后补：

- 总结模型润色
- Web 管理页
- 人工复核页面
- 报账场景

## 5. 关键配置项

建议配置项包括：

```env
WECHATY_PUPPET=
WECHATY_TOKEN=

DATABASE_URL=
STORAGE_DIR=

QWEN_API_KEY=
QWEN_BASE_URL=
QWEN_VISION_MODEL=qwen3-vl-flash

DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=
DEEPSEEK_SUMMARY_MODEL=deepseek-v4-flash

DEFAULT_TIMEZONE=Asia/Shanghai
```

场景配置建议独立成配置文件：

```yaml
channels:
  - code: loss_main
    scenario: loss-report
    roomTopic: 门店食材报损群
    summaryCron: "0 22 * * *"
    deliveryTargets:
      - type: contact_name
        value: 你的主微信昵称
```

## 6. 测试策略

### 手工测试

- 纯文字报损
- 纯图片报损
- 图片 + 文字报损
- 多物品报损
- 模糊图片
- 重复消息

### 自动化测试

优先做这些单元测试：

- 群路由逻辑
- 去重逻辑
- 报损场景结构化结果校验
- 汇总统计逻辑
- 日报模板渲染

不建议第一阶段做的自动化测试：

- 真正的微信登录 E2E

这类测试不稳定，第一阶段应以手工联调为主。

## 7. 后续扩展路线

当你要接入报账群时，目标是只新增以下内容：

- `src/scenarios/reimbursement/*`
- 报账场景相关数据库表
- 群配置
- 对应模型路由配置

理论上不应修改：

- Wechaty 接入主流程
- 消息标准化逻辑
- 通用附件存储
- 通用发送模块

如果后续新增场景时不得不频繁改这些主干模块，说明当前平台边界设计有问题，需要及时回头修正。

## 8. 预计开发顺序建议

建议按下面顺序真正动手：

1. 搭项目骨架
2. 跑通微信监听和发消息
3. 落原始消息和图片
4. 跑通报损提取
5. 跑通日报
6. 加稳定性
7. 再做多场景扩展

## 9. 当前阶段建议决策

现在就可以确认的决策：

- 技术栈选 `Node.js + TypeScript`
- 架构选 `模块化单体 + 场景插件`
- 第一场景选 `报损群`
- 汇总频率选 `每日一次`
- 回传目标选 `你的主微信号`
- 模型组合选 `Qwen3-VL-Flash + DeepSeek-V4-Flash`

如果接下来进入编码，应该先从 `Milestone 1` 和 `Milestone 2` 开始，而不是先写模型逻辑。
